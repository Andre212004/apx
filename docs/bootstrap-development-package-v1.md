# APX Bootstrap Development Package v1

Status: closed package-definition and rebuild-evidence contract. No package has
been built, signed, trusted, installed, or admitted by this repository work.

## Purpose and Name

The first package rehearsal is deliberately named
`apx-contracts-development`. It is an unsigned development package, not the APX
bootstrap package promised for a real installation. It exists only to prove
that a small reviewed set of non-mutating contracts can be assembled twice
from the same frozen source and produce identical evidence.

It does not provide an `apx` command, broker, executor, installer, service,
PAM integration, Hub, Environment root, or host-changing operation. Installing
it cannot make a machine APX-functional.

No extra entry, generated bytecode, source checkout metadata, cache, credential,

## Reproducible Build Inputs

One definition binds:

- exact source revision and complete source-tree SHA-256;
- package version and release number;
- `SOURCE_DATE_EPOCH` derived from the frozen revision, not wall-clock time;
- fixed dependency and forbidden-feature sets;
- the ordered entry list and every source digest;
- a canonical definition digest.

The future isolated builder must use a clean exported source tree. A dirty
working tree, Git checkout embedded in the package, network access during
build, mutable dependency resolution, or current-time timestamp blocks the
rehearsal.

Two builds count as an exact match only when definition identity, final package
SHA-256 and size, canonical `.PKGINFO`, `.BUILDINFO`, `.MTREE`, and internal
member-manifest digests all agree. The isolated builders must expose the same
canonical build path and frozen installed-package/tool inventory because Arch
records both in `.BUILDINFO`. A successful comparison proves deterministic
bytes for this small package; it does not establish production trust.

## Deliberate Blockers

The repository licence is now `Apache-2.0`, but the relevant work is not a clean
committed source revision. Therefore creating a release-pinned Arch `PKGBUILD`
and claiming a completed package would still be premature. A frozen clean
source, reviewed build flags/tool versions, two isolated builds, and retained
evidence are required next.

Production signing remains a later, separate ceremony. Development keys or
signatures must never be relabelled as the offline APX root or release-signing
authority.
